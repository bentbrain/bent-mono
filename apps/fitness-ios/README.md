# bent Fitness

The native iPhone app for [Fitness](../fitness/README.md). It plans and logs dumbbell strength sessions and runs, tracks food and bodyweight, shows progress, and syncs Apple Health weigh-ins and running workouts in the background. It covers everything the Fitness website does, with the same rules, and works offline with changes saved on the iPhone until Fitness can be reached.

- **Week:** the week board with each day's planned, done and missed sessions, the day's plan, starting and resuming workouts, logging runs, dragging sessions to other days of the week and resetting the week, and weekly totals.
- **Workouts:** sets with weight, reps or seconds per side, reps in reserve and control, a rest timer and session timer that keep running across screens, backgrounding and restarts, a hold timer for timed exercises such as planks, typed values kept on the iPhone until saved, notes, finishing and discarding. The screen stays awake during a workout, and a Live Activity on the Lock Screen and in the Dynamic Island shows the current set and counts down each rest and hold.
- **Exercises:** every guide with its illustration, setup, steps, what to watch for, how to record it, the current prescription, the last result and the YouTube tutorial. Workouts and plans open the guide as a sheet.
- **Food:** the day's calories and protein against targets, and carbs, fat and fibre for the nutrients chosen under Profile and targets, meals with add, edit and remove, saved meals in one tap, and the last seven days as a chart that shows each day's calories, protein and difference from the target.
- **Progress:** sessions by week, strength by exercise, the bodyweight trend, history with corrections, removing and restoring workouts and runs, and weigh-ins with the 7-weigh-in average. Each chart shows the details of the point you touch.
- **Reminders:** a daily notification at the time you choose that says what's planned for the day, such as "Today: Strength A" with its exercises and length, or an easy run, with rest days included if you choose. Tapping it opens that day in the Week tab.
- **Widget:** a Today widget for the Home Screen and the Lock Screen with the day's session and whether it is planned, in progress or done, and the day's calories, protein and tracked nutrients against their targets.
- **Settings:** profile and targets, the nutrients to track, the repeating week with routines and exercises, equipment and private equipment photos, reminders, Apple Health sync, the account export, managing the account and signing out.
- **Apple Health:** new weigh-ins and runs sync in the background whenever iOS wakes the app, and each time the app comes to the foreground. The first sync sends your chosen history while the app is open.

## The app

The app is Expo and React Native. Each tab is a native stack under iOS's native tab bar (React Navigation's native bottom tabs with `react-native-screens`), with large titles, form sheets and SF Symbols. Colours are semantic tokens in `global.css`, used through Uniwind classes, with light and dark variants; the primary colour is the shared bent.build accent from `@bent/design-tokens`. Segmented controls and date pickers are SwiftUI views from `@expo/ui`, and charts are Swift Charts views from the local `fitness-charts` module. The domain rules, schemas, progress summaries and exercise guides come from `@bent/fitness-contracts`, the same code the website runs.

- `src/account`: the session. Signing in opens Clerk's sign-in in a private browser session with PKCE (S256) and a random `state`, requesting `openid`, `offline_access`, `fitness:read`, `fitness:write` and `fitness:health:enroll` for the Fitness MCP endpoint. The refresh token is kept in the Keychain (`AfterFirstUnlockThisDeviceOnly`); access tokens stay in memory and refresh a minute before they expire, one refresh at a time. A refresh Clerk refuses signs the app out. Signing out revokes the refresh token and deletes the account's data on the iPhone; Apple Health sync stays connected until it is disconnected under Settings › Apple Health; while signed out, the sign-in screen opens Apple Health sync, and a pending consent or Health step opens there at launch.
- `src/data`: the Fitness app API client (`/api/app`, described in the Fitness README) and the sync engine. Every request names the records contract the build reads in `X-Fitness-Contract`. Requests belong to the sign-in they started under, so a reply that arrives after signing out or switching accounts is dropped, and a refresh that finishes after signing out revokes what it received. Every change is a mutation with the record's expected revision and a new operation ID, queued in SQLite and sent in order, as the website does. The app keeps the last records it loaded, so it opens with them offline. Loads and saves run one at a time in the order requested, so a load reflects every save acknowledged before it, and each save's queue entry and records are stored in one transaction. After a pass that saved changes, the account loads again, so a record removed on another device doesn't stay on the iPhone. A record another device changed stops the queue; the sync sheet shows both versions, exports the queued changes and typed workout values, and keeps the cloud version when chosen. A change Fitness refuses as invalid holds the queue until it is discarded from the same sheet. The app asks iOS to exclude the SQLite database from iCloud and computer backups when it opens it; if iOS refuses, the app keeps working and asks again on the next launch. The header of each tab shows the save state and opens that sheet.
- `src/screens`: one folder per tab, plus `health` for Apple Health sync and `root` for sheets above the tabs.
- `src/screens/week/workout`: the workout logger. A timed set has **Start hold**, which counts down 5 seconds to get into position, then the set's target seconds; exercises held on each side count the left side, 5 seconds to switch, then the right. The target is the seconds typed in the set, else its saved value, with the same rules as the set's field, so decimal seconds are kept; the set's seconds fields are locked while its hold runs. When the hold ends, the set records the target and is marked Done, which starts the exercise's rest. **Stop and record** saves the whole seconds held on each side reached and leaves the set open. The hold runs on this iPhone only and is not saved with the workout; starting one ends a rest that is running. Each phase is worked out from the hold's start time, and the hold is kept outside the logger while the app runs, so a hold keeps going after leaving the workout, and one that ended while the logger was closed or the app was in the background is recorded when the workout opens again.
- `src/ui`: the shared controls: text, buttons, inset-grouped lists, cards, notices, fields, segmented controls and date pickers.

Exercise illustrations load from the Fitness origin and stay in the image cache. Equipment photos load from `/api/app/photos` with the access token; signing out clears the image cache.

## Live Activity

The `workout-activity` module shows a Live Activity while a workout is in progress. It shows the workout, elapsed time, the next set with its weight and rep range or hold length, sets handled, and a countdown during a rest or hold. The logger starts and updates it as sets are handled and rests and holds start and end; the countdowns run on the Lock Screen without the app. The activity goes out of date at the end of a rest, or of a whole hold, and then shows "Rest done" or "Hold done" with the next set; a local notification at that moment plays a sound. While the app is suspended it can't move a hold to its next phase, so during a hold the activity also counts down to the end of the whole hold. iOS asks for notification permission the first time a rest or hold starts; without it, the activity still changes. Each alert has its own identifier and generation, so a skipped rest, a new rest or a cancel removes an alert still waiting for permission. Finishing or discarding the workout ends the activity; so does the end of the sign-in, by signing out or when Fitness ends it, which also forgets any hold. The Week tab ends activities for workouts finished or discarded on another device.

The activity has no push updates: ActivityKit passes its content to the extension directly. The module's config plugin sets `NSSupportsLiveActivities`, adds the `WorkoutActivityExtension` widget extension target, which compiles `modules/workout-activity/ios/Extension` and `ios/Shared` in place and also holds the [Today widget](#today-widget), and lists the extension with its entitlements under `extra.eas.build.experimental.ios.appExtensions` for EAS signing. Its bundle ID is the app's followed by `.workout-activity`. Live Activities can be turned off for the app in Settings › bent Fitness.

## Reminders

Settings › Reminders turns on a daily workout reminder and sets its time and whether rest days get one. The screen shows the next reminder as it will read, with the day and time it fires in the account timezone. These settings are kept in the app's database on this iPhone, for whichever account is signed in, and are not part of the Fitness account. Turning reminders on asks for notification permission if iOS hasn't asked yet; if notifications are off for the app, the switch stays off and the screen explains how to allow them in iOS Settings. If notifications are turned off in iOS Settings later, the switch keeps showing the setting and the screen says that reminders can't show until notifications are allowed again; turning the switch off works either way.

Reminders are local notifications that the `workout-activity` module schedules with `UNUserNotificationCenter`, using the identifier prefix `build.bent.fitness.workout-reminder.` and one request per day, so they never replace the timer alerts. The app keeps the next 14 days scheduled at the chosen time in the account timezone, from today, or from tomorrow once today's time has passed. A time a daylight-saving change skips fires just after the change, and a time that happens twice fires the first time. Each reminder follows the Week tab's plan for its day, dated plans and workout corrections included:

- A strength day names the routine, its exercises and its length: "Today: Strength A", "6 exercises · about 45 min".
- A run day says "Today: Easy run".
- A rest day gets "Today: Rest day" with the next session, when rest-day reminders are on.
- A day with a recorded or started session gets no reminder. A workout removed from history, or moved to another day, no longer counts for its original day.

The app schedules the reminders again after each load or save that changes the records or the plan, when the reminder settings or the day change, and each time it comes to the foreground, so finishing today's session on the iPhone removes today's reminder if it hasn't fired. Each schedule keeps the pending reminders that are unchanged, removes the ones no longer planned and adds the new ones, so a reminder about to fire is never removed and added again too late. If iOS refuses to add a reminder, the app schedules again a minute later, as long as the same sign-in lasts. A reminder planned before a change on another device fires as planned until the app next opens.

While the app is open, a reminder shows as a banner; timer alerts show nothing, as the logger gives its own haptic. Tapping a reminder opens the Week tab at its day, including when the tap launches the app, ahead of a widget link and of returning to a waiting Apple Health step. Each reminder names the account it was scheduled for, and a tap opens its day only while that account is signed in. Signing out, or the end of the sign-in, removes pending and then delivered reminders, forgets a tap not yet handled, and none are scheduled while signed out.

## Today widget

The Today widget shows the day in the account timezone. One widget adapts to each size:

- **Small:** the session with its state and length, and calories and protein against their targets.
- **Medium:** the session on the left, and bars for calories, protein and each tracked nutrient on the right. A nutrient tracked without a target shows its grams. Tapping the session opens the Week tab at that day; tapping the food opens the Food tab.
- **Lock Screen, rectangular:** the session, its length or state, and "1125/2400 kcal · 57/120 g protein".
- **Lock Screen, circular:** a calorie gauge that opens the Food tab.
- **Lock Screen, inline:** the session and the day's calories, such as "Strength A · 1125 kcal".

The session follows the Week tab's plan, dated plans included, with the same names and lengths as the reminders: a strength routine with its exercises and about how long it takes, an easy run, or a rest day with the next session. A finished session shows as done, and a workout started that day as in progress with its sets handled. Calories over the target, a carb or fat target passed, and protein or fibre reached each show in their own colour. The widget uses the app's accent and semantic colours in light and dark, takes on the tint of a tinted Home Screen, and lets the system shape the Lock Screen sizes. The small, medium and rectangular sizes open the Week tab and the circular size opens the Food tab, at the day shown. The plan and food are marked privacy-sensitive, so iOS redacts them wherever it hides private widget content, such as on the Lock Screen of a locked iPhone.

At launch the app opens a tapped reminder first, then a tapped widget link, and only then returns to a waiting Apple Health step, once it knows the app wasn't opened from either. A reminder or widget tapped while the app starts, including while it is still loading the account, replaces the launch destination; the latest tap wins.

The widget extension can't sign in or load the account, so the app writes a snapshot for it to `Library/Application Support/widget/today.json` in the App Group container it shares with the extension, `group.` followed by the app's bundle ID. The snapshot holds the plan and food totals for today and the next six days, each with the moment its day starts and ends in the account timezone, and the links to the Week and Food tabs. The widget's timeline starts a new day at each midnight in the account timezone, with food back at zero against the targets, so it moves on without the app; after the last day it asks to open the app. The app writes the snapshot after each load or save, when the plan, targets or tracked nutrients change, when the day changes and each time it comes to the foreground, skips a snapshot the same as the last one, and then asks WidgetKit to reload the widget. A session recorded on another device shows once the app next opens. The file is protected until first unlock, and its folder is excluded from backups. When the widget can't read the file, as before the first unlock after a restart, it tries again 15 minutes later.

When the session closes, by signing out or at the end of the sign-in, the app drops every snapshot still waiting from that sign-in and replaces the file with one that holds no account data, and the widget asks to sign in. If that write fails, the app deletes the file. If both fail, signing out says that some data was left on the iPhone, and the app tries again each time it comes to the foreground while signed out.

## Apple Health sync

1. **Connect.** Settings › Apple Health › Connect Apple Health gets a new access token from the account's session and keeps it in memory for this connection.
2. **Enroll.** `POST /api/health/devices` exchanges that token for a device key. The key is stored in the Keychain (`AfterFirstUnlockThisDeviceOnly`) in a waiting state; nothing is read from Health or sent yet. Each attempt sends `enrollmentSequence`, one higher than the last attempt from this installation. The count is stored in the Keychain before the request goes out, so it keeps rising across relaunches and lost replies. Of the successful replies, the app keeps the key with the highest sequence, whatever order the replies arrive in; a success from a lower sequence is revoked, and a failed attempt leaves the stored key in place. A connection begins one enrollment attempt before it gets the token, and each of its requests, retries included, passes that attempt. A disconnect or a declined consent cancels the attempt: a request that has not been sent stops without sending, a failure that arrives afterwards ends the connection instead of being retried, and a success that arrives afterwards is revoked. Busy and unavailable replies, and `409 stale_enrollment`, are retried with the same token and a new sequence after exactly `Retry-After`; if the token would expire first, the app asks to connect again later. Replies that use up the token ask to connect again, and each refusal has its own message.
3. **Consent.** The consent screen shows the account email, the data types, the destination, when syncs happen, what Disconnect does and how much history to send. Confirming or cancelling names the enrollment the screen shows, so it never acts on a key for another account that replaced it in the meantime; the app then asks to check the screen again. Confirming activates the key with an absolute start date. Cancelling revokes the key. Nothing registers for Health updates while consent is pending.
4. **Health access.** iOS asks which types the app can read: Weight, Workouts and Walking + Running Distance. The app then shows the earliest weigh-in and run it can read since the start date, or that it can read none, and, on iOS 27 when the user shared limited history, the earliest date Health allows. The first sync starts only from this step's Start button; the app stores that it is waiting, so a relaunch opens Settings › Apple Health at this step, as it does while consent is pending, and nothing syncs before it.
5. **First sync (backfill).** The app records where each type's history ends, then sends whole days in the account timezone in order, with `expectedTimezone`. A request gathers whole days up to about 200 samples; a day with more goes on its own, in chunks of up to 2,000 samples, Fitness's limit per request. Days are built with a calendar in the account timezone, and every boundary is the start of its own day, so a daylight-saving change at midnight or at 23:00 drops no hour. It marks a day done only after every request for it succeeds. If the account timezone changes, it regroups from the start date. Changing the history to send rebuilds the recorded positions from the new start date and stops a backfill in progress, so a later start date leaves out history the earlier one covered, deferred samples included. When it reaches today, incremental sync takes over from the recorded position.
6. **Incremental sync.** Each page of up to 200 new samples is one request, and its position is saved only after Fitness accepts it with one outcome per sample. HealthKit observer queries and background delivery wake the app for new data; each run takes background time before it starts and completes HealthKit's handlers exactly once. When that time runs out, the run's writes close: a checkpoint write in progress finishes first, and none starts after. Each checkpoint write runs together with its session check on the device lifecycle, so a history change or a disconnect either stops it or waits for it and then rebuilds or clears what it wrote.

Samples dated after now wait until they are due. A run without a distance waits 6 hours for one. After that it is sent without one, and Fitness saves it as 0 km, only when Health reports that the app can read distance from a date at or before the run's start. Health does not say whether read access was denied, and a readable distance from another time says nothing about this run. On iOS 27, `getEarliestAuthorizedSampleDate(for:)` reports that date when the user shared limited history. With full access, before iOS 27, in a build made with an SDK that lacks the lookup (Xcode 26), when the lookup fails, or when its answer leaves distance out, the app can't tell a run with no recorded distance from one whose distance it can't read. Those runs wait. The status screen shows how many are waiting for distance access, with one button to send them without a distance. The button names the runs the screen showed and the current enrollment. The app approves them only if that enrollment is still active and exactly those runs are still waiting. If a sync added or removed a run in the meantime, nothing is sent, and the screen shows the new count for another tap. A run that starts waiting later needs its own choice. A run whose distance could not be read is never sent as 0 km. The distance comes from the workout's statistics, then its associated distance samples, then its total distance.

The app keeps sample UUIDs, positions and per-run counts in `Application Support/sync/<account>/state.json`. Its directories are excluded from backups before the first write, and each write replaces the file atomically with protection until first unlock already applied. Before the first unlock after a restart, the Keychain and state stay as they are and the app tries again once the iPhone is unlocked; a file holding no Health data or key records whether sync is on, so observers register at launch. It keeps no Health values. Disconnect stops using the key and clears that file first, then stops the current run and the observers, then revokes the key with `DELETE /api/health/devices/current`, retrying on later launches if the iPhone is offline and waiting for `Retry-After`, counted from the reply, when Fitness asks. A key Fitness will not revoke because it is not a device key is counted, and the Connect, reconnect and status screens show a notice to revoke it under Manage account → API keys until it is dismissed; the count outlives the disconnect. Dismissing names the count the notice showed, so a key refused after the notice appeared stays on it, and it changes nothing about the key or a sync in progress. If an upload gets `401 key_invalid`, the app clears that key, if it is still the stored one, and asks to connect again. This also recovers when a later connection replaced the key on the server but its reply was lost. Logs carry codes and counts only, and the app has no analytics.

## Variants

| Variant       | Bundle ID                | Redirect URI                     | Fitness origin                                    |
| ------------- | ------------------------ | -------------------------------- | ------------------------------------------------- |
| `development` | `build.bent.fitness.dev` | `build.bent.fitness.dev://oauth` | `https://fitness.bent.build`, or `FITNESS_ORIGIN` |
| `production`  | `build.bent.fitness`     | `build.bent.fitness://oauth`     | `https://fitness.bent.build`                      |

`APP_VARIANT` selects the variant and defaults to `production`. Build settings:

- `FITNESS_OAUTH_ISSUER`: Clerk's OAuth issuer, such as `https://clerk.example.com`. Development builds also accept `http://127.0.0.1`.
- `FITNESS_OAUTH_CLIENT_ID`: the "Fitness iOS" OAuth application's client ID.
- `FITNESS_ORIGIN` (development only): another Fitness origin, HTTPS or `http://127.0.0.1:<port>`.

These are public values. Without the OAuth settings, the app says sign-in is not set up in the build. The native module pins every request to the build's Fitness origin and refuses redirects to another origin.

## Development

Use Node.js 24, Bun 1.4.4, Xcode, CocoaPods and SwiftLint. From the repository root, run `bun install --frozen-lockfile`. Generated `ios/` stays out of the repository.

```sh
cd apps/fitness-ios
bun run typecheck && bun run lint && bun run knip && bun run test
bun run config:development
node scripts/native.mjs prebuild    # ios/ for APP_VARIANT
node scripts/native.mjs build       # Simulator build
node scripts/native.mjs core-test   # XCTest for the Swift module
node scripts/native.mjs lint        # SwiftLint
```

Build output goes to `NATIVE_BUILD_DIR`, or `~/Library/Caches/fitness-ios-build`.

`modules/fitness-charts` is a local Expo module that draws the line and bar charts with Swift Charts in a native view. JavaScript passes each chart's values, its colours from the theme tokens, and a title and detail lines for every point or bar. Tap a chart to select the nearest point; touch and hold, or drag sideways, to move the selection with your finger. The chart draws a cursor at the selected point, highlights it, shows its title and details in a card beside it, and gives a selection haptic each time the point changes. The selection stays when you lift your finger; tap the selected point again to clear it. A vertical drag scrolls the screen. The card wraps to at most 240 points wide; when it is taller or wider than the chart, as with larger text sizes, the details show below the chart instead. VoiceOver reads each chart's summary, and swiping up or down on a chart moves the selection and reads each point's title and details. The lists beside the charts give every value.

`modules/fitness-health` is a local Expo module. `ios/Core` holds the sync engine with no HealthKit or UIKit dependency, and `ios/Package.swift` builds it with its XCTest suite on its own. `ios/Platform` adapts it to HealthKit, the Keychain, files, `URLSession` and background time, and `ios/Module` exposes it to JavaScript. The config plugin adds the HealthKit and background-delivery entitlements and the Health read purpose string.

### Simulator

A Simulator build signed to run locally, with no paid team, carries its HealthKit entitlements in the binary's `__entitlements` section, and HealthKit works with them: the app requests read access and reads samples another app wrote.

`tools/health-seed` is a separate Simulator-only Xcode project. Its Health Seed app (`build.bent.fitness.healthseed`) asks for write access and writes synthetic samples relative to today: weigh-ins over three days, two on one day, and one two days ahead; an outdoor run and a treadmill run with distance; a run without distance; and a run whose distance sample is attached after the workout is saved. Each sample has a sync identifier, so seeding again replaces it. Launch it with `-action seed` or `-action clear` to run without a tap. bent Fitness can read these samples only when its own read access is allowed, since another app wrote them.

XCUITest drives the Health access sheet, which appears in the requesting app's window. `SimulatorFlows/HealthSheet.swift` allows or denies with it:

- The "Select All" cell has the identifier `UIA.Health.AuthSheet.AllCategoryButton`, and each type has a switch.
- The confirming button at the end of the list is Allow. On iOS 27.2, a read-only request, like the one bent Fitness makes, shows Continue instead.
- On iOS 27.2, a read request then asks how much history to share: "Past 30 Days and Future Data" or "All Recorded Data and Future Data". Allow stays disabled until one is chosen. The Health step shows the earliest weigh-in and run the app can read, so a 30-day choice shows there.
- Don't Allow is followed by an alert saying categories can be turned on later in the Health app.
- The read sheet notes that background access follows Settings → General → Background App Refresh.

On a newly booted Simulator, the sheet can take more than 20 seconds to appear, and HealthKit's request can fail with "Authorization session timed out" before it does. The flows ask again when that happens.

### Simulator flows

`scripts/flows.mjs` builds the development variant against a local harness, then runs each flow on a new Simulator, once more on another new Simulator if it fails. `node scripts/flows.mjs <flow>` runs only the named flow, such as `testDeniedHealthAccessSendsNothing`. `node scripts/flows.mjs --build-only` builds the development app and the seeder against the harness without a database, and `node scripts/flows.mjs --prebuilt [flow]` runs the flows on such a build in `NATIVE_BUILD_DIR`: the app under `app/Build/Products` and the seeder's test run file and products under `seeder/Build/Products`. Each attempt starts with `POST /__reset`, which gives the harness an empty account and zero request counts. The harness serves every flow, so it runs with `FITNESS_TEST_DEADLINE_MS=3600000` in place of the Fitness tests' 15-minute deadline. In every flow, the harness counts no imports before consent, after a relaunch at the consent screen, or after a relaunch at the Health step.

- **Denied:** sign in, connect Apple Health from Settings, confirm consent, deny Health access. The app shows that it can read nothing, the sync sends no import request, and Disconnect revokes the key.
- **Allowed:** sign in, connect Apple Health from Settings, confirm consent, allow Health access to all history. The sync sends the earliest weigh-in for each seeded day and three runs: 5 and 4.2 km recorded with their workouts, and 3.1 km from the distance sample attached after the workout was saved. The run without a distance waits for distance access, and the weigh-in dated ahead waits until it is due. A second Sync now, waited for by its own completion time, sends no import request. Send 1 run without distance then sends the waiting run, which Fitness records as 0 km.
- **Partial:** sign in, connect Apple Health from Settings, confirm consent, allow Weight and Workouts but not Walking + Running Distance. The weigh-ins sync, no run is sent as 0 km, and the status screen says runs are waiting for distance access.

The harness (`apps/fitness/tests/ios-simulator.harness.test.ts`) serves the real Fitness device, import and app API handlers on Postgres with the synthetic Clerk fake, plus a synthetic OAuth server that signs in a synthetic account, checks the PKCE verifier and redirect URI, and issues refresh tokens. No Clerk instance or secret is involved. `POST /__seed` fills the account with three weeks of synthetic workouts, runs, meals and weigh-ins, and tracks carbs and fibre. The harness serves the records contract the build declares.

`SimulatorFlows/ScreenTourTests.swift` signs in through the harness and captures each screen as a PNG, and each chart again with a point selected (the files ending in `-popover`). The tour fails when a chart is missing or a tap on it selects no point. With a development build installed and the harness running and seeded, run it with `-only-testing:SimulatorFlows/ScreenTourTests` and the `TEST_RUNNER_FITNESS_SIM_ORIGIN` and `TEST_RUNNER_FITNESS_TOUR_DIR` environment variables. Set the Simulator's appearance with `xcrun simctl ui <device> appearance dark` to capture dark mode. `-only-testing:SimulatorFlows/ScreenTourTests/testWorkoutActivityTour` starts today's workout, captures a plank hold and a rest, and captures the Dynamic Island from the Home Screen; use an iPhone Simulator with a Dynamic Island. The harness seed makes today a strength day with a timed exercise. `-only-testing:SimulatorFlows/ScreenTourTests/testRemindersTour` captures Settings and the Reminders screen and allows notifications. Restart the Simulator with `xcrun simctl shutdown` and `boot`, since SpringBoard delivers an app's local notifications once it starts with the app's permission in place, then run `testRemindersDelivery`: it checks that reminders stay on after the restart, sets a reminder a few minutes ahead, taps its banner while the app is in the background, and taps the next one's banner after closing the app, checking each time that the Week tab opens at the reminder's day.

```sh
docker run -d --rm --name fitness-ios-pg -e POSTGRES_USER=test -e POSTGRES_PASSWORD=test \
  -e POSTGRES_DB=fitness_test -p 55432:5432 postgres:16
FITNESS_TEST_DATABASE_URL=postgres://test:test@127.0.0.1:55432/fitness_test node scripts/flows.mjs
docker stop fitness-ios-pg
```

Background delivery is not available in the Simulator. Background and locked-device behaviour is checked on an iPhone.

## Tests

- `bun run test`: the sync engine (queue order, offline start from the saved records, conflicts, stale editors, account changes), the session (refresh, rotation, expiry, sign-out), each tab's rules, the reminders (their text, the 14-day window, the account timezone and daylight-saving changes, rest days, recorded sessions, dated plans, and the order of schedules and cancels), the widget snapshot (its days and their midnights in the account timezone, daylight-saving changes, session states, food against targets and tracked nutrients, links, the signed-out snapshot, the order of writes around signing out, and deleting the file when the signed-out snapshot can't be written), the launch destination (a reminder, then a widget link, then a waiting Health step, and taps that replace it), the theme tokens, the Health screens, consent copy, error guidance, the retry rules for connecting, the variants and the release checks.
- `node scripts/native.mjs core-test` (also `bun run native:test`): the sync engine with fake HealthKit and a fake Fitness ledger, covering backfill by account day, daylight-saving changes at midnight and at 23:00, resuming, split days, timezone changes, cutoff changes, deferred and unreadable samples, run distance and distance access, lost replies, interrupted checkpoints, expiry and write fencing, checkpoints racing a history change or a disconnect, distance coverage from Health's answer, a locked Keychain, the coordinator, the device lifecycle with overlapping enrollment attempts and sign-ins cancelled mid-retry, consent tied to its enrollment, and revocation timing. It also decodes every committed reply in `apps/fitness/tests/fixtures/wire/replies` with the production decoder.
- `node scripts/roundtrip.mjs` (needs `FITNESS_TEST_DATABASE_URL`): Swift encodes synthetic requests, `apps/fitness/tests/ios-roundtrip.test.ts` sends them to the real import handler as a device key and records real enrollment, import and disconnect replies, and Swift decodes them. The replies cover each outcome the requests produce, `timezone_changed`, `too_many_samples`, `rate_limited`, `issuance_pending` and `issuance_failed` with `Retry-After`, Clerk outages on every route, both `Authorization` forms, and a disconnect retried after its reply was lost.
- `node scripts/fingerprint-check.mjs`: the native fingerprint stays the same after a JavaScript change and changes after a Swift or config plugin change.
- `node scripts/flows.mjs`: the Simulator flows above.

## CI

Quality runs two jobs for this app:

- `fitness-ios` (Ubuntu), on pull requests, the merge queue and main: typecheck, lint, knip, unit tests, `expo config` for both variants, `expo-doctor` and the fingerprint check.
- `fitness-ios-native suite` (macOS 26 with Xcode 26.6), on pull requests, the merge queue, scheduled runs and dispatch: SwiftLint, production prebuild, Simulator build, the artifact check, the seeder build, the XCTest suite, and, with a temporary Homebrew `postgresql@16`, the round trip. It runs when the change reaches this app, `packages/fitness-contracts` or `apps/fitness`, including through a workspace dependency, when it changes a native root input, and on full runs. `iosNativeInputs` in `scripts/ci-scope.mjs` lists the native root inputs: the root `package.json`, `bun.lock`, `bunfig.toml` and `turbo.json`, `.github/actions/setup`, `.github/codeql`, the Quality and Fitness iOS Verification workflows, and `scripts/ci-scope.mjs`, `scripts/require-ios-native.mjs` and `scripts/check-sarif.mjs`. Documentation and other root files leave the suite out. On main pushes, Quality leaves the suite to Fitness iOS Verification, which runs the same steps: the production build and the native checks in its Production build job, and the seeder build in its Simulator flow build job. The required `fitness-ios-native` check passes when the suite passes or when the run leaves it out.

Fitness iOS Verification (`.github/workflows/fitness-ios-verify.yml`) runs on main pushes that touch a path in `iosNativeInputs`, daily at 17:00 UTC, and on dispatch. Those paths are the native root inputs, this app and the workspace code it builds and tests against. It reports on main, and releases do not wait for it. Four jobs on macOS 26 start together on the repository's five macOS runners. The app and modules CodeQL jobs start when the CodeQL build finishes, and the three Simulator flows when the flow build finishes, each when a runner is free:

- `CodeQL Swift build`: builds the production app once for the app and modules jobs, compiling whole-module and reading the app target's bridging header as source, on the arm64 slice, unoptimised and without a dSYM. It keeps the generated Xcode project, the build log and the derived data, without the objects, archives and bundles, as a one-day workflow artifact, with the checkout and build paths it used. The SDK stat caches are left out: they hold the build runner's file IDs, so the app and modules jobs make them again with `clang-stat-cache`, as the build log records.
- `CodeQL Swift (app)` (with Rosetta): unpacks the CodeQL build at the same paths, failing when the paths differ, then traces Xcode's logged arm64 Swift compile commands for the app target with the Swift prebuild generates and the widget extension. Traced, every process runs under Rosetta, which makes a whole Xcode build of the app take over an hour. With the bridging header precompiled by Xcode's clang, the extractor records nothing for the app target. `codeql-coverage.mjs --scope app` checks that the extension's sources, the workout-activity sources it shares and every Swift file the app target compiles were extracted.
- `CodeQL Swift (modules)` (with Rosetta): unpacks the CodeQL build the same way, then traces the fitness-health, fitness-charts and workout-activity modules' logged compile commands. The two jobs split the targets so their replays take about the same time: the first target each job replays spends about 8 minutes building the module cache under Rosetta, then the widget extension and the fitness-health module each take a few minutes more. Each stops at 25 minutes. `codeql-coverage.mjs --scope modules` checks that the fitness-health module's Core, Platform and Module sources, the fitness-charts module's sources and the workout-activity module's Module and shared sources were extracted.
- `CodeQL Swift (tools)` (with Rosetta): builds Health Seed and its UI tests, then traces their logged arm64 compile commands and a build of the module's Swift package with its XCTest targets into one database. `codeql-coverage.mjs --scope tools` checks that the seeder's Swift and the module's Core and Tests sources were extracted.
- `Production build`: the rest of Quality's native suite: the production prebuild, Simulator build and artifact check on the arm64 slice, SwiftLint, the module's XCTest suite, and the round trip on a temporary Postgres.
- `Simulator flow build`: `node scripts/flows.mjs --build-only` builds the development app against the local harness and the seeder with its UI tests, on the arm64 slice without an index store or a dSYM, and keeps them as a one-day workflow artifact.
- `Simulator flow (denied)`, `Simulator flow (allowed)` and `Simulator flow (partial)`: each unpacks the flow build and runs one flow with `node scripts/flows.mjs --prebuilt <flow>` against the local harness on Postgres; none builds the app. `FITNESS_FLOW_BUDGET_SECONDS` ends the flow 22.5 minutes after the job started, however long setup takes, leaving 2.5 of the job's 25 for uploading a failed flow's results and stopping Postgres, each limited to a minute. Each attempt, from resetting the harness to the end of its test, finishes with 2 minutes kept for its log and the Simulator's removal and 30 seconds for the harness to stop; a harness still running then is killed and fails the run. Booting a Simulator has 4 minutes and installing the app 3, so a slow Simulator ends its attempt early. The retry on a new Simulator starts only when at least 8 minutes are left before that cleanup time, so the job's limit never cuts an attempt or its cleanup short. A launch that XCTest records as failed, such as one that timed out, or a failed check that later steps depend on ends the flow at once, so the retry keeps its time. A Simulator that can't be deleted fails the run, which names it. The flow build is kept for a day, so rerunning only the failed flows works on the same day; after that, rerun the whole workflow.
- `Fitness iOS verification`: passes when every job above passes.

The CodeQL builds compile one arm64 Simulator slice with `-Onone`, `GCC_OPTIMIZATION_LEVEL=0` and DWARF debug information without a dSYM, which is the slice the trace compiles again. Each CodeQL job uses both security suites under its own category, `fitness-codeql-swift-app`, `fitness-codeql-swift-modules` or `fitness-codeql-swift-tools`, and `scripts/check-sarif.mjs` requires zero raw findings from each. Each analysis runs with `upload: never` and `upload-database: false`. Each job keeps its original SARIF as the `codeql-swift-app-original-sarif`, `codeql-swift-modules-original-sarif` or `codeql-swift-tools-original-sarif` workflow artifact for 90 days. The Swift reports stay in these artifacts and the run's log, and the Security tab lists Quality's CodeQL analysis. The coverage check fails when a tracked Swift file in the repository belongs to none of the app, modules and tools scopes.

Job time limits: the Quality `fitness-ios-native suite` stops at 20 minutes. In Fitness iOS Verification, the tools CodeQL job stops at 27 minutes, the CodeQL build, the production build and the flow build at 20, the app and modules CodeQL jobs and each flow at 25, and `Fitness iOS verification` at 2. With every job at its limit, a build, a flow or CodeQL replay and the aggregate take 47 minutes, plus any time a job waits for a runner. Measured on dispatched runs: 22 minutes for the tools CodeQL job, 11 for the production build with the native suite's checks, 11 for the flow build and 7 to 10 for each flow, or up to 19 when a flow retries. The app scope took 26 to 28 minutes in one job, so it is split into the app and modules jobs, which share one build.

The artifact check reads the production Simulator build: exactly the HealthKit and background-delivery entitlements and exactly the App Group `group.build.bent.fitness`, with no other capability and an application identifier of a team ID followed by the bundle ID, the Health read purpose string and the write purpose string saying the app saves nothing to Apple Health, no local networking, `NSSupportsLiveActivities`, the App Group in `FitnessAppGroup`, the fitness-health, fitness-charts and workout-activity modules linked in, with the workout-activity module's reminders and widget snapshot, the widget extension in `PlugIns` with the Live Activity and the Today widget, exactly the same App Group and no other capability, its own bundle ID and application identifier, and the App Group in its own `FitnessAppGroup`, and no seeder files or symbols. Besides the capabilities, an entitlements list may hold only the keys Apple's signing adds: `application-identifier`, `com.apple.developer.team-identifier`, `get-task-allow` as a Boolean, `beta-reports-active` and `keychain-access-groups`. Expo leaves out a local module whose minimum iOS version is above the app's, so each module's podspec matches the app's iOS 16.4.

`expo-doctor` runs with `EXPO_OFFLINE=1`, which checks package versions against the installed SDK's `bundledNativeModules.json`, so a new SDK release changes no Quality result. `react` is excluded from its version check: the workspace uses React 19.3.1, and SDK 58 lists 19.3.0. To move to a newer SDK release once it is a day old, run `bunx expo install --check` in this directory and commit the updated versions.

## EAS

`eas.json` has `development` and `production` profiles with Node 24, Bun 1.4.4 and the `macos-tahoe-26.5-xcode-26.6` image, and requires a committed tree. The EAS project and its owner are in `app.config.ts`. After installing dependencies on EAS, the `eas-build-post-install` script fails the build unless the image reports Xcode 26.6, the version CI builds and analyzes, and prints `Verified Xcode 26.6.` when it does. Production submissions go to the App Store Connect app that `submit.production.ios.ascAppId` names.

Each EAS environment sets the build's public OAuth settings: `FITNESS_OAUTH_ISSUER` and `FITNESS_OAUTH_CLIENT_ID` for that environment's Clerk instance and its Fitness iOS application. The `production` environment uses the production instance.

## Release

The **Deploy Fitness iOS** workflow (`.github/workflows/deploy-fitness-ios.yml`) builds an exact main commit on EAS and submits it to TestFlight. Run it from the Actions tab on `main`, with the full 40-character commit SHA of the current `main` head as `sha`. To release, dispatch Deploy Fitness iOS for the current main commit once Quality has passed on it, then approve the `fitness-ios-production` environment. The `fitness-ios-production` concurrency group runs one workflow run at a time. Every run builds the commit afresh from its checkout: a rerun after a failure starts a new build, and a commit with any submitted build is refused. A build started directly in EAS for the same commit is outside the concurrency group, and can still race a run.

It needs a GitHub environment named `fitness-ios-production`:

- Deployment branches: `main` only.
- Required reviewer: the repository owner, who approves each run before it starts.
- Secret `EXPO_TOKEN`: the access token of a robot user in the `bentbuilds-team` organization, which owns the EAS project, with the lowest role that can build and submit. Not a personal or owner token. Only the steps that run the EAS CLI, or ask EAS for builds' submissions, receive it.

The workflow, on `macos-26`:

1. Requires `sha` to be the commit the run started from, and checks it out without keeping credentials.
2. Requires the commit to be current `main`, merged from a pull request whose head passed native CodeQL, and independent review when it changed application, package or release code, with every Quality job passed, using the same gate as the other deploy workflows. It checks again immediately before `eas build` and immediately before `eas submit`, and stops if the Quality run changed or a newer Quality run started for the commit.
3. Checks that the checkout has no `.easignore` and that `eas.json` pins the EAS CLI version, which it installs, and writes the static EAS directory described below.
4. Checks the production iOS build settings twice: as `scripts/release-ios.mjs` resolves them, with the profile's `extends` chain and then its `ios` settings applied, and as the pinned EAS CLI's own `@expo/eas-json` resolves and converts them. The build must be a Release store build of the production variant in the `production` environment, on `macos-tahoe-26.5-xcode-26.6`, with remote credentials and `autoIncrement: true`. `simulator`, `developmentClient` and `withoutCredentials` must be absent or `false`, and a custom build config, prebuild command, scheme or enterprise provisioning must be absent; eas-json reads `"true"` as `true`, so each value must have its exact type.
5. Reads `FITNESS_OAUTH_ISSUER` and `FITNESS_OAUTH_CLIENT_ID` from the `production` EAS environment, checks that the issuer is an HTTPS origin and the client ID only letters, digits, hyphens and underscores, writes them to a private file under `$RUNNER_TEMP` that later steps read by path and check again, and checks them against production:
   - `fitness.bent.build/.well-known/oauth-protected-resource` must name that issuer as its only authorization server.
   - `/api/health/devices/ready?clientId=<client>` must reply `200 {"enrollment":"enabled"}`, while an unlisted client gets `403 client_not_allowed`.
   - The issuer must offer every scope the app requests (`openid`, `offline_access`, `fitness:read`, `fitness:write` and `fitness:health:enroll`) with PKCE S256, and must know the client. The check reads the instance's sign-in page from `<issuer>/v1/environment` and starts an authorization request with the client, the production redirect URI, the app's scopes, the MCP resource, a random state and an S256 challenge, without following redirects or signing in. `/oauth/authorize` must send it to that sign-in page, returning to the issuer's own `/oauth/authorize-with-immediate-redirect`; that step must send it to the sign-in page again, returning to `/oauth-consent` on the same accounts host. Each step must answer with a 301, 302, 303, 307 or 308 redirect, the sign-in page and both returns must be HTTPS on the default port with no user information and no `#`, and both returns must carry the request's eight authorization parameters exactly. Clerk answers an unknown or deleted client with `invalid_client`, a redirect URI the client does not have with `invalid_request`, and a scope the client may not request with `invalid_scope`, and any of these, or any other redirect, stops the release.
6. Lists the commit's production iOS builds with `eas build:list`, asks EAS for each build's submissions, and refuses if any build has one, whatever its status. Then it installs the workspace with the frozen lockfile, checks that the checkout is still clean and at the commit, and runs `eas build --profile production --platform ios --non-interactive`.
7. Requires one finished store build of the production bundle ID from exactly that commit in this EAS project, with the Xcode check in its log. It writes each signed archive and log URL into a private curl config file, and `curl` downloads them, following up to five redirects and only over HTTPS; a failed download shows only curl's exit code. It then verifies the app's code signature, nested code included, with `codesign --verify --strict --deep`, and checks the `.ipa`: exactly the HealthKit and background-delivery entitlements and exactly the App Group `group.build.bent.fitness`, no other capability, `get-task-allow` absent or `false`, exactly the production application identifier under the signing team, the Health read purpose string and the write purpose string saying the app saves nothing to Apple Health, no local networking, `NSSupportsLiveActivities`, the App Group in `FitnessAppGroup`, the fitness-health, fitness-charts and workout-activity modules linked in, with the workout-activity module's reminders and widget snapshot, the widget extension with the Live Activity and the Today widget, signed with exactly the same App Group, no other capability, `get-task-allow` absent or `false` and exactly the production extension identifier under the app's team, with its own bundle ID and the App Group in its `FitnessAppGroup`, and no seeder. Its embedded app config must be the production variant with the checked issuer and client, and its version and build number must match the EAS build and be one to three period-separated whole numbers. CI builds only for the Simulator, so the first release run is the first to check a signed App Store archive.
8. Reads the EAS environment again and requires the same issuer and client, checks production and the issuer again, checks that `fitness.bent.build/privacy` serves the privacy policy, and requires that EAS lists no submission of the new build. Then it submits that build with `eas submit --id <build> --no-auto-testflight-setup`, so EAS creates no TestFlight groups and invites nobody. Builds reach testers through the internal TestFlight group "bent Fitness Internal", which has access to all builds and is managed in App Store Connect. Afterwards it reports the submission's ID and status, and fails unless the submission finished.
9. Writes the status, commit, build ID, version and build number to the run summary, each checked again (a known status, a UUID build ID and Apple's version format), and removes the archive, the OAuth settings file, the EAS output, the EAS CLI and the static EAS directory whatever the outcome. It uploads no GitHub Actions artifacts; EAS Build itself uploads the source archive. It never prints the signed URLs.

Every EAS step that holds the Expo token, apart from the build, runs in `$RUNNER_TEMP/eas-static`: `env:list` both times, `build:list` and `submit`. That directory holds only a `package.json` with no dependencies or scripts, a static `app.json` with the app's name, slug, owner, bundle ID and EAS project ID and no plugins, and the checked `eas.json`. The project metadata is read from `app.config.ts` and `src/config/variants.ts` as text, without running them. These steps set `EAS_NO_VCS=1`, `EAS_PROJECT_ROOT` to that directory and `EXPO_NO_DOTENV=1`, so the EAS CLI reads only those files: with no `expo` dependency it never starts the workspace's Expo CLI, and it runs no app config, plugin or `.env`.

`eas build` runs in `apps/fitness-ios` with the token, because it uploads a git archive of the exact commit. It evaluates `app.config.ts`, the fitness-health config plugin (for the entitlements) and `metro.config.js` from the clean, reviewed `main` commit, installed from the frozen `bun.lock`, inside the owner-approved environment. That is the same source the EAS builder runs. It sets `EXPO_NO_DOTENV=1` and `EAS_SKIP_AUTO_FINGERPRINT=1`. The workspace is installed only for this step, after the other pre-build EAS steps.

Each EAS CLI step writes the CLI's output and errors to private files under `$RUNNER_TEMP`, since its messages can carry signed URLs or account details. The log shows only a fixed message with the exit code when a step fails, and the build ID, submission ID and status that the checks validate. The checks read each capture strictly: a reply that is not valid JSON, or whose values fail validation, stops the release with a fixed message that names only the file, never its contents. Build and submission IDs must be UUID strings before they are shown or passed to a later step. The submission lookups give `curl` the token as a header line on stdin, and every `curl` runs with `-q` so it reads no `.curlrc`. Error messages name a provider's error code only when it is one the provider documents: the codes Fitness's `/ready` route returns, or the OAuth 2.0 error codes Clerk's authorize steps return. Any other reply shows only its HTTP status, and a failed request names its endpoint, never a URL from the EAS environment.

Each step has a time limit; the build has 150 minutes and the job 240. `scripts/release-ios.mjs` holds the checks, as subcommands that read and write files under `$RUNNER_TEMP`; its tests also check the workflow itself.

Builds and submissions use the signing credentials and the submission key stored in EAS: the distribution certificate, an App Store provisioning profile for the app and one for the widget extension (`build.bent.fitness.workout-activity`), and the App Store Connect API key for EAS Submit. Both App IDs must have the App Group `group.build.bent.fitness`, and both provisioning profiles must include it; the production profiles in EAS do. The release builds with `--non-interactive`, so the App IDs, the App Group and both profiles must exist in EAS before a release. To set them up again, run `eas credentials --platform ios` from `apps/fitness-ios` in a terminal, signed in to Expo, with `EXPO_ASC_API_KEY_PATH`, `EXPO_ASC_KEY_ID`, `EXPO_ASC_ISSUER_ID`, `EXPO_APPLE_TEAM_ID` and `EXPO_APPLE_TEAM_TYPE` set for the App Store Connect team key. The submission key can also be added under the project's credentials on expo.dev.

TestFlight builds expire after 90 days. Release again before then to keep the app installed.

[`fitness.bent.build/privacy`](https://fitness.bent.build/privacy) is the app's privacy policy, for App Store Connect.
